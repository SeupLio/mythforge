# ADR-0001：32 位定长寄存器字节码

- 状态：已采纳（切片 A）
- 关联模块：M3 codegen、M4 VM

## 背景

任务/剧情脚本实例数量可能到万级，且需要热重载。指令格式同时影响：

- VM 的分发成本（每条指令的解码 + 分支预测）；
- 模块体积与加载校验复杂度；
- 编译器的寄存器分配与跳转修补；
- 热更包的差分粒度。

## 决策

采用**定长 32 位**指令，寄存器式（而非栈式）：

```
bits  0..7   opcode
bits  8..15  operand A（通常是 dst）
bits 16..23  operand B（src / 常量索引 / 跳转偏移低 8 位）
bits 24..31  operand C（src / argc / 跳转偏移高 8 位）
```

- 三地址算术：`ADD dst, src1, src2`，一条指令完成，不需要 push/pop。
- 常量与寄存器索引 8 位：每 chunk ≤ 255 个寄存器、≤ 256 个常量；越界由编译期诊断（MFC4002/MFC4003）而不是运行时崩溃。
- 跳转：无条件和条件跳转都用 8 位寄存器 + 16 位有符号偏移（相对下一条指令），偏移范围 ±32767，越界报 MFC4005。
- 一个 chunk = 一个 handler（`<quest>/start` 或 `<quest>/on_<Event>`），天然形成可热替换的编译单元。
- 指令流按块顺序布局，跳转在代码生成末尾统一回填（patch list）。

## 取舍

**相对栈式字节码**：同样的 `a + b * c`，栈式需要 5 条左右（push a / push b / push c / mul / add），寄存器式 2 条。指令数少意味着分发次数少、调试信息更紧凑。代价是指令更宽（32 位 vs 8 位），但 quest 脚本的代码量远小于数据量，收益更大。

**相对 64 位指令**：64 位可以支持更大的常量池和寄存器，但会让每条指令的 cache 占用翻倍。当前限制（255 寄存器）对任务脚本足够，超出时按 handler 拆分，这也符合「一个任务一个编译单元」的热更边界。

**相对变长指令**：变长会让解码多一次边界判断，且跳转回填需要处理指令边界。定长换来的是 `code[pc]` 直接索引，校验器可以 O(n) 扫描。

## 后果

- 编译器必须做 phi 消除和并行复制，把 SSA 值映射到固定帧槽位（无溢出，因为帧在堆上按需分配）。
- 大 handler 会触发寄存器上限；这是有意的护栏，避免隐式拆分导致的调试信息错位。
- 分发目前用 `switch`。后续在 GCC/Clang 上加 computed goto（MSVC 保留 switch 回退），并用同一套微基准对比，作为 M4 的性能证据。
- 所有指令在加载时由 `verifyModule` 做结构校验（操作码、寄存器范围、常量类型、跳转目标、谓词索引），损坏或篡改的热更包在执行前就会被拒绝。
